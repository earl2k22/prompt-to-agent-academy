# Lesson 1.1 — How Language Models Interpret Prompts

**Status:** Published · **Phase:** Prompt Engineering Foundations · **Estimated time:** 35–45 minutes

## Learning outcomes
By the end of this lesson you can: (1) explain a prompt as a specification plus relevant context, (2) distinguish an instruction from background data, (3) make an ambiguous request concrete, and (4) design a safe prompt with verifiable completion criteria.

## Core concept
A language model predicts and generates responses based on the instructions and context it receives. It cannot reliably infer every unstated preference or constraint. A prompt is therefore a *communication interface*: it should convey what success looks like and what not to do.

The useful five-part framework is **Goal → Context → Constraints → Acceptance criteria → Verification**. A short question may only require the goal; complex coding work benefits from all five.

### Worked example
**Vague:** "Check my Ubuntu PC and make it faster."

**Better:**
- **Goal:** Diagnose slow application startup on Ubuntu without making system changes yet.
- **Context:** Ubuntu desktop; symptoms began after installing developer tooling.
- **Constraints:** Read-only inspection. Do not uninstall packages, edit configuration, run privileged commands, or delete files.
- **Acceptance criteria:** Give three evidence-based likely causes, ranked by impact, with links between each claim and an observed command result.
- **Verification:** Explain how I can check the findings, and propose changes separately for approval.

**Why it improves the task:** It narrows scope, prevents unintended changes, and defines evidence and stop conditions.

## Technical vocabulary
- **Goal:** the desired outcome, not merely an activity.
- **Context:** task-relevant facts and references.
- **Constraint:** a hard limitation on permitted results or actions.
- **Acceptance criterion:** a condition by which a person can determine success.
- **Verification:** the checks or evidence used to confirm a criterion.

## Guided practice
Rewrite: "Make me a good Python app." Include the users, core action, environment, non-goals and at least three testable acceptance criteria.

## Practical lab — Safe Ubuntu agent
Write a prompt for an AI agent to inspect (not fix) developer-environment problems on Ubuntu. Specify:
1. What it may inspect (read-only environment and tool versions).
2. Commands/actions that require your approval.
3. What report it must produce.
4. How it should report uncertainty or missing evidence.
5. How it knows the diagnosis step is complete.

## Checkpoint questions
1. Why is "be very intelligent" not a measurable acceptance criterion?
2. What is the difference between context and a constraint?
3. How would an agent know it should stop before modifying files?

## Self-assessment rubric (0–2 points each)
- Goal is unambiguous.
- Context is adequate but concise.
- Scope and approval boundaries are explicit.
- Acceptance criteria are observable.
- Verification and final report are specified.

**Target:** 8/10 or higher. Review weaker dimensions before proceeding.

## Reflection
Compare your version against the original weak prompt. Identify one unclear assumption you resolved and one action you explicitly prohibited.
