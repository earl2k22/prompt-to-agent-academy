# Teaching and content quality standard

All lessons should be accessible to a motivated beginner but technically accurate for engineering work.

## Required sections
1. Title, stable ID, estimated time, publication state.
2. 3–5 measurable learning outcomes.
3. Short explanation and conceptual model.
4. At least one weak-to-strong worked example.
5. 3–8 terms with accurate definitions and practical applications.
6. Guided exercise and hands-on lab.
7. Verification steps and evidence of success.
8. Checkpoint questions, answer guidance or rubric, and reflection.
9. Sources where factual, security, or tool behavior claims require verification.

## Voice
Be direct and concrete. Define terms before using them. Avoid jargon inflation: an impressive word never replaces a testable requirement. Do not use vague encouragement in place of correction. Distinguish stable principles from rapidly changing vendor features.

## Verification
- Check examples for executable correctness where possible.
- Security restrictions must be enforced by tools, not prompt text alone.
- Report limitations honestly; do not claim a build or deployment succeeded without evidence.
- Use actual user examples: Ubuntu, VS Code, GitHub, Codex, OpenCode, Ollama.
